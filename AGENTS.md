# BaseballO Repository Instructions

- The canonical remote is `https://github.com/CarterBeauBenson/BaseballO.git`.
- The Git repository root contains the active project in `Baseball/`.
- Do not initialize another Git repository inside `Baseball/`.
- Repository controls such as `.github/`, `.editorconfig`, `.gitattributes`,
  `AGENTS.md`, and the public README live at the Git root. Application and research artifacts live under
  `Baseball/` according to `Baseball/REPOSITORY-LAYOUT.md`.

  to push the completed work. Follow the branch and publishing rules below.

## Project guardrails

- The user is the ontologist. Do not modify files under `Baseball/ontology/` unless the user explicitly requests an ontology change. Report ontology gaps for the user to decide.
- Do not create new object properties. Reuse accepted BFO/CCO relations and model the full supported pattern; when that is insufficient, document the gap. Agreement with a natural-language description does not authorize a new predicate. The user clarified this prohibition on 2026-09-09 after identifying the four runner properties as a misunderstanding. Renaming those relations into an index namespace does not resolve the underlying semantic gap.
- Use free and open-source infrastructure. The intended pipeline stack is Apache NiFi and Apache Jena Fuseki/TDB2.
- Never rewrite raw source bytes. Preserve the existing checked-in evidence corpus unchanged. New API responses are transient pipeline inputs: retain their hashes and manifests, remove their raw JSON only after successful graph-pair promotion, and retain failed inputs only for quarantine and retry.
- Keep the NiFi semantic ingester enabled. External MLB acquisition runs daily at 05:00 Eastern under the user's explicit authorization; change or disable that schedule only at the user's direction.
- Submit NiFi work asynchronously by default. Do not continuously monitor a healthy run; inspect status only when the user asks or when NiFi records a failure.
- Codex is a coder and reviewer, not the routine workflow engine. Put repeatable acquisition, dependency ordering, mapping, validation, reasoning, benchmarking, promotion, materialization, retry, quarantine, and provenance work in NiFi. Codex authors and reviews the components and the evidence that NiFi produces.
- The user decides semantic meaning and major lifecycle topology. The accepted broad lifecycle is `API -> RML -> SHACL -> Fuseki -> queries -> SQL -> UI`. Within an accepted semantic design and that topology, Codex owns the engineering: processor reconciliation, locking, retries, staging, manifests, fingerprints, indexing, physical SQL design, equivalent query optimization, tests, and UI plumbing do not require file-by-file approval.
- The retired NiFi control plane is not a source for the replacement flow. Do not restore, migrate, inspect, or reproduce its global reconciliation framework. Build source-isolated lanes from the accepted lifecycle and current semantic components.
- NiFi's separate `Repository Evidence` group owns the implemented aggregate repository gate as an asynchronous observer. Use only focused developer checks for changed components; do not reproduce the aggregate stage by manually chaining every repository check.
- Manual commands are limited to the smallest focused developer check for the component currently being changed and user-requested diagnostics. If a check or transformation will be needed repeatedly, make it an idempotent NiFi-owned stage or a component invoked by one; do not leave Codex as its scheduler or operator.

## Semantic modeling and source-extension gate

- BaseballO is a realist ontology project, not a source-schema-to-RDF conversion project. Model the entities, qualities, relations, roles, acts, processes, sites, and temporal structure in reality before modeling information about them.
- Do not infer an occurrent's type from the fact that it is governed, prescribed, scheduled, or described by a Plan or Rule. Prescription is a relation, not a taxonomic shortcut. A temporally extended whole may be a BFO Process with intentional Planned Acts as occurrent parts; classify each level by its own differentia.
- Do not infer the type of a whole from the types of its parts, or the type of a part from its containing whole. Parthood, participation, prescription, governance, and contextual association are not subclass relations.
- Admit a proposed Act only when at least one Agent plays a causative role at that Act's own level. Admit a Planned Act only when, additionally, a Directive Information Content Entity held by at least one of its Agents prescribes that Act. Require an Objective or other intentional structure only where the selected subclass requires it. Do not inherit agency, prescription, or intention from an enclosing process, an outcome label, a governing Organization, or a source record. Otherwise use the correct Process category or leave the term unresolved.
- Use `agent in` or `has agent` only when the asserted Agent is causally active as an Agent in that Process. Governance, affiliation, hosting, benefit, organizational context, or authorship of a Plan does not by itself make an Organization the Agent of the Process prescribed by that Plan.
- Before proposing a membership, status, assignment, or affiliation Role, test whether an accepted Occupation Role or other existing Role plus `has organizational context` and a temporally bounded Stasis of Role already expresses the fact. A grounding relation or temporal qualification does not by itself license a new Role universal.
- Do not model Team-to-Division, Team-to-League, Person-to-Team, or similar institutional membership as continuant parthood between Object Aggregates. Represent the bearer-specific Organization Member or Occupation Role, its organizational context, and its reviewed temporal persistence instead.
- A Stasis represents persistence or absence of the relevant change; it does not realize a Role, Disposition, or Function. Assert `realizes` only from the Process in which the realizable entity is manifested. A Role and its bearer may participate in a reviewed Stasis of Role, but that participation never substitutes for realization.
- Keep Role identity separate from realization-event identity. Reuse a career- or tenure-persistent Role with its bearer across the Processes that realize it; do not mint one Role per event. A generic Process or Act used as a common event grain requires explicit semantic review, but an accepted common grain must not be removed merely because more specific event subclasses are also available.
- For an organization-context Role whose identity is one continuous stint, reuse that Role throughout the uninterrupted bearer-Organization stint and timebox its persistence with a Stasis occupying a Temporal Region. Moving away and later returning creates a new Role and a new Stasis; adjacent observations alone do not prove continuity. This does not apply to career-persistent participation Roles such as Batter Role merely because their realizations occur for different Teams.
- When evidence supports the beginning or ending of a particular Role, represent that change with the accepted CCO Gain of Role (`cco:ont00001194`) or Loss of Role (`cco:ont00000613`). Each transition is a Process that occupies its own Temporal Region; use Stasis of Role (`cco:ont00000824`) for the intervening persistence interval. The independent bearer participates in the transition, and `affects` must identify the exact Role that changes. If that Role identity is unsupported, do not assert the transition. Stasis does not realize the Role. Gain or Loss typing alone does not license a `realizes` relation to the affected Role; any such relation requires independent evidence at the appropriate event grain. A provider label, mentioned Organization, or date value does not by itself license a transition: require evidence for the bearer, Role identity and organizational context, direction, and temporal precision.
- Do not turn a temporary context into an intrinsic primitive kind of its bearer. Prefer querying through the Role, organizational context, realization, and Temporal Interval. A contextual bearer class is permissible only as an explicitly reviewed defined query view equivalent to that full pattern; it must not replace the Role or erase the particular Game or time scope.
- Historically scoped institutional assertions such as affiliation, membership, status, assignment, and home-venue assignment must use an accepted temporalized relation, stasis/history pattern, or explicitly scoped intermediary when the dataset represents their validity across time. A clearly documented snapshot assertion may use an accepted binary relation when that relation's semantics support the snapshot. Never treat words such as "during season" in a label, comment, or Mermaid edge as executable temporal semantics. If no accepted pattern can express the intended historical claim, record the gap and stop.
- Information Content Entities are about entities in reality; they do not replace those entities. Keep a source record, data-element ICE, measurement ICE, measured entity, measurement process, unit, estimate, classification, and adjudication distinct whenever the evidence supports those distinctions.
- Never hide an unmodeled quality, relation, geometry, process profile, or identity criterion inside the label or definition of a field-specific ICE. In particular, a measurement ICE is not the speed, angle, distance, trajectory, or other entity it measures.
- Do not use BFO or CCO Spatial Region classes in BaseballO domain modeling. For field-relative geometry, use the reviewed continuant-side pattern of Fiat Points, Fiat Lines, Fiat Surfaces, Sites, Relational Qualities, and a generic Reference System ICE. If removing Spatial Region semantics leaves the referent or relation unresolved, record the gap and stop; do not substitute another spatial class by label.
- Source, provider, record grain, and provenance normally distinguish ICE instances, not ontology universals. Create an ICE subclass only for a source-independent intensional differentia needed for reasoning; model provider code systems as Reference System individuals unless an independently justified universal exists.
- Do not create one ontology class per API field, CSV column, source code, provider label, or analytical output. A source field licenses a mapping only after its meaning, referent, identity scope, unit, provenance, and missing-value behavior are understood.
- Reuse accepted BaseballO, BFO, and CCO classes and relations first. If the required world-side referent cannot be expressed with accepted vocabulary, record an ontology gap and stop that field; do not work around the gap with a new ICE class, literal, comment, or untyped IRI.
- The user is the ontologist. New classes, axioms, definitions, and identity policies require explicit review. New object properties are prohibited by the guardrail above. Proposed classes use one named BFO/CCO-grounded parent, reviewed axioms in the overlay, and a singular Aristotelian genus-and-differentia definition with complete annotations.
- SPARQL and SHACL over accepted terms and accepted graph contracts do not require a new ontology proposal. Codex may author and revise analytical SPARQL and may encode accepted competency-question or graph-contract decisions in SHACL. Stop for ontologist review only when that work would introduce a new ontology term, axiom, identity policy, object property, or genuinely new modeling assumption.
- Every ontologically load-bearing genus, differentia, and relation named in a definition must resolve to an accepted term or an explicitly reviewed proposal term, and the OWL axioms must state the same structure. Undefined technical phrases and comments cannot carry missing semantics.
- Definitions and axioms require an independent semantic anchor. Do not define a closed cluster of new terms only through one another, and do not claim that necessary restrictions capture a class when the identity-bearing differentia remains unmodeled. Acknowledging the gap in a comment does not cure it; block the term.
- A Relational Quality proposal must identify the multiple non-identical independent continuants on which it specifically depends and its temporal scope with accepted relations. Where fiat or frame-relative relata are used, identify the continuant wholes or reference frame required by the identity account. A Process Profile proposal must identify the profiled Process and the dependent pattern of change it profiles. If the ontology cannot connect that structure, leave the proposal unresolved rather than putting the relation only in the class name or definition.
- Model a changing speed, velocity, acceleration, or similar dependent pattern as a CCO Process Profile that is an occurrent part of the profiled motion Process. A Measurement ICE measures that Process Profile and carries its value and unit; do not attach one scalar to the whole Process as though it were constant. Use Speed for a scalar magnitude. Use Velocity only when direction, axes, signs, origin, reference frame, and evaluation scope are represented.
- A CCO Artifact Function requires evidence that its Material Artifact bearer was designed for Processes requiring that Function and may remain unrealized. Mere selection, assignment, or historical participation does not establish an Artifact Function; use an accepted Role or other reviewed pattern when design is absent. A class restriction must not falsely entail an actual realization.
- General instructions such as "continue," "execute," "finish," or "take in this source" are not approval for a new semantic assertion or a new pipeline topology. Approval must identify the proposal or named modeling decision being accepted. Once the user approves the semantics or topology, do not ask them to approve the ordinary engineering files needed to implement it.
- Never write, infer, or promote an ontologist-approval status on the user's behalf. Never refresh a semantic freeze, curation-debt baseline, or admitted semantic fingerprint unless the user explicitly accepts the named review package in the current conversation.
- When Git is authorized, record an accepted semantic or major-topology decision in a separate commit and push before implementing its ontology, identity, RML, SHACL, reasoning, materialization, or UI consequences. A review record created alongside its implementation is retroactive documentation, not prior approval. This ordering protects decisions, not implementation trivia: after acceptance, Codex chooses and changes the necessary engineering artifacts without requiring an exhaustive `authorizedArtifacts` list.
- Before extending any source family, create a field-level selection inventory that marks each field as already supplied by an authoritative source, deterministically derivable, identity/join-only, genuinely additional, or unresolved. Do not remap duplicates or derived values merely because another provider exposes them. A field already present in the authoritative payload remains a duplicate even when the current RML omits it; that is mapping-coverage debt in the owning lane. Wider endpoint population or history does not by itself make the assertion type semantically new.
- The required implementation order is: competency questions and source evidence; de-duplication inventory; source-independent Mermaid shapes; ontologist review; accepted ontology/identity changes; source-specific Mermaid and RML; one-record fixture; one-game RDF plus SHACL and semantic inspection; only then bounded corpus ingestion, serving materialization, or UI exposure.
- Translate every accepted competency-question answer that constrains an RDF graph into the owning source module's SHACL profile. NiFi must run that profile after RML and before promotion. Use SPARQL regression checks for analytical questions that are not conformance constraints. Supporting scripts may invoke SHACL, serialize reports, and check source or RDF mechanics, but must not duplicate the accepted semantic decision as imperative graph-review code.
- Review-only Mermaid diagrams must exist and be approved before executable RML is written for a new source family. Generated post-implementation Mermaid remains a non-regression check and does not substitute for that prior design review.
- Every novel BaseballO class, object property, or data property declared in a proposal Turtle file must be enumerated exactly in that package's `review.json` `proposedIris`; restatements of already accepted terms for repair are not novel. Every artifact hash recorded in a draft review must match the current package-relative file. Leave an artifact list empty while it is still changing rather than retaining a stale pin.
- Proposal terms must never appear in executable RML, SHACL, SPARQL contracts, authoritative RDF, serving schemas, or UI code before acceptance. A successful or unusually fast transformation is not evidence of semantic correctness.
- Stop at the first failed gate. Do not allow implementation momentum to carry an unresolved modeling assumption from ontology into RML, corpus loading, SQL, or the UI.
- Do not bypass semantic validation with `--no-verify`, by weakening a validator or CI rule in the same change, or by relabeling known debt as accepted. Changes to semantic governance controls receive the same review protection as ontology and mapping artifacts.
- A source may be operationally active while its semantic surface is frozen. In that state, the pinned pipeline may continue under the documented runtime policy, but ontology, RML, source SHACL, context construction, and semantic query assumptions may not expand until the named blockers receive ontologist review.

## Detachable source-module architecture

- Every external or derived source is a detachable module under `Baseball/sources/<source-id>/`. Its source contract, executable RML, source-specific SHACL, and every source-specific NiFi process group must be owned by that module.
- RML and source-specific SHACL must never cross source boundaries. A mapping may transform only its declared source; a source validation profile may constrain only that source's promoted graph contract.
- The authoritative triple store is the integration boundary. Join sources only after independent validation and promotion, using SPARQL that explicitly declares whether it is single-source, multi-source, or derived in `Baseball/sparql/source-scope-catalog.json`.
- Give re-identifiable persistent entities such as Persons, Venues, Teams, Leagues, and Divisions source-owned authority products when the source contract supports stable identity. Distinguish those products from event-scoped evidence for one-time Processes and Acts: event RDF remains persistent evidence, but an event is not a reusable identity authority in the same sense as a persistent continuant. When one source response supports both kinds, explicitly review whether supporting occurrent evidence stays with its authority record or is promoted as a separate source-owned graph product; do not infer placement merely from the provider or RDF type.
- Stopping, removing, or rebuilding one source module must not stop unrelated modules. Already promoted authoritative RDF remains persistent unless the user explicitly authorizes its removal; indexes and SQL serving products remain derived and rebuildable.
- Shared mapping files are limited to source-neutral identity and modeling policies. Shared SHACL is limited to genuinely source-neutral derived-layer contracts; convenience is not a reason to create a cross-source executable file.
- NiFi owns separate source lanes through acquisition, mapping, source validation, promotion, retry, quarantine, and provenance. Cross-source and serving work may begin only from successful promoted-graph events and must declare its upstream modules.
- Do not extend an existing source module merely because a provider is the same organization. MLB games, other MLB APIs, Statcast, weather, and travel/rest are separate modules with separate failure and disconnect boundaries.
- Do not pre-create placeholder directories, graph namespaces, NiFi groups, RML, or SHACL for a future source. Declare them when that source module reaches review and can own the complete boundary.
- Keep exactly one active review catalog at `Baseball/proposals/`. Move accepted or rejected work to `Baseball/archive/design-records/` with its disposition; do not create proposal directories under ontology, Mermaid, mappings, or a source module.
