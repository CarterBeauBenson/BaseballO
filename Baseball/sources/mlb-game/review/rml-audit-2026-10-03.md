# October 3 RML execution audit

This pass examined the recorded repair queues and the readers that carry RML
inputs and execution-context evidence into NiFi manifests. It changes no
ontology, RML triple map, context selector, source SHACL or semantic freeze.

## History repair request collisions

The discovery inventory contained **146 failed entries** with
`Recorded history repair request changed`. These failures were upstream of
mapping and were not visible in the per-game history worker's success counts.
For example, game 822687 retained a request for promotion
`77941652adc34cd3adc3ed9817cd672ee3e75955b9f4ce8aadc0aa45a76a5ad6`
under the previous `86f6f6ad...` context. The approved F5/D2 context is
`73bd4ef2...`; discovery tried to store its new request at the old filename.

Requests now use a digest of their complete contents, so a different approved
selector creates a separate request without overwriting the old one. If the
game, promotion, manifest, recorded failures and authorized scope are unchanged,
the worker reuses the existing hash-verified response. Its original acquisition
request and receipt remain intact. The new selection's request is recorded
separately on the repair case. A change beyond the selector hash still fails
the scope comparison; this does not authorize substituting another source or
rebuilding a game. Discovery prioritizes previously failed entries while
retaining its existing bounded scan and one-source-per-tick behavior.

The regression reproduces a legacy request followed by a newer selector,
preserves both the original request and acquisition bytes, selects only the
missing history, and verifies that no API fetch occurs. Changed scope and
modified acquisition evidence remain rejected.

## Defensive retry ordering

There were still 20 defensive failures from the older `781e5faa...` worker.
Every failed input was present. Meanwhile, 100 input-cache entries had been
rechecked by the newer worker, with hundreds of older successful entries still
ahead of later games. Ordinary rechecks were delaying the recorded failures.

The existing defensive worker now places available witnesses for failed

A regression checks both priority and the unchanged retry limit.

## UTF-8 context and manifest reads

The context builder writes UTF-8 without a byte-order mark. Windows PowerShell's
default `Get-Content` decoding corrupted non-ASCII text when that context was
copied into the RML manifest. Retained evidence confirmed this in game 822693
(`NuÃ±ez` instead of `Nuñez`) and game 822809 (`AndrÃ©s GimÃ©nez` instead of
`Andrés Giménez`).

The RML harness and the MLB-game stage and query-index repair readers now
explicitly use UTF-8. A regression executes the production PowerShell read
statements and source-read function using a real sample's accented description,
then checks exact round-trip values and unchanged input bytes.

This fixes subsequent evidence production and copying. Historical manifests
are preserved with their original hashes; they are not silently rewritten or
relabeled. The mapping engine already reads the original UTF-8 inputs, so this
finding does not justify RDF regeneration.

## Admission writer race

A further pass found an evidence-writer race in game 822896. Its independent
pitch-count receipt was committed at 12:31:57 UTC on October 2, then the proof
was overwritten at 12:31:58 by an unwrapped admission result. The receipt and
proof hashes differed. The periodic admission worker ran outside the lease
already shared by the targeted workers that also refresh these proofs.

Admission maintenance now uses that same existing repair lease. On a recorded
`Existing graph admission receipt changed` failure for the current promotion,
the evidence owner preserves the mismatched directory and all original bytes
under `admission-refresh/interrupted/`, with their hashes and recovery intent.
It then uses the ordinary retained-input/census and SHACL paths to produce fresh
evidence. Recovery itself admits nothing and does not acquire data, execute
RML, change RDF, update semantic pins or rewrite the original failed evidence.
Previously failed games receive their bounded retry ahead of successful
maintenance after a worker-code change.

Focused regressions check the actual maintenance wrapper holds the repair
lease, the lease releases on failure, the interrupted bytes remain intact,
unrelated failures and valid receipts are untouched, and the ordinary retry
limit and multi-stage continuation still work.

## Completing the recorded retry backlog

The next pass found that discovered history jobs reused per-game completion
solely from equal `selectedHistoryKeys`, including two empty lists. For example,
822687's current repair request had a different promotion and retained witness
from its older evidence-only completion. Discovered completions and retry
allowances now bind the exact request hash and source hash. Deferrals do not
consume failure attempts.

The same NiFi history worker now processes at most ten cases per tick and stops
starting cases after 45 seconds. Defensive repair handles at most three under
the same time rule. Both are serial and retain the shared repair lease plus
each game's existing lock; the Python lock was checked against the PowerShell
lock. A stage already underway finishes normally. No new lanes or schedules
were added. Discovery and reading valid existing proof receipts can proceed
with 256 MiB available; history mapping or fresh SHACL still needs the full
1 GiB reserve. Defensive execution keeps that full reserve too.

Independent admission refresh now checks its existing receipt loaders before
exporting RDF or opening Jena. This uses precisely the existing validator's
skip condition, preserves conclusive withheld results, verifies the retained
source hash, and does not replace a proof with an unchecked success.

Fuseki's unused committed heap also contributed to the runtime deferrals.
Its existing 256 MiB minimum and 1 GiB maximum remain; free-heap ratios are now
20/40 with a 60-second idle periodic collection interval. These are the
[JDK 21 G1 heap-sizing controls](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html).
The live change required no service restart: committed heap fell from 1 GiB to
529 MiB, and available system memory reached about 2 GiB. The same settings
are in the startup script so this recovery does not depend on repeated manual
garbage collection. Focused regressions cover request identity, memory
deferral, bounded serial execution, cross-language locking and proof reuse.

The smaller heap did not by itself remove the memory deferrals: Fuseki's
working set later reached 2.4 GiB with a 527 MiB committed Java heap, while
available RAM fell below 600 MiB. The existing repair budget now asks Windows
to release this project's Fuseki working set when available RAM is below
1 GiB and that process occupies more than 1 GiB. It verifies the recorded PID,
Java executable and exact server jar before calling
[EmptyWorkingSet](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-emptyworkingset).
Pages may be loaded again on demand, so this can temporarily slow graph reads;
it does not stop Fuseki or change its graphs. The worker then rechecks the
unchanged memory reserve and defers if it remains unavailable. This runs under
NiFi's existing serial repair lease. Regression coverage checks reserve
rechecking, unsuccessful reclamation and rejection of an unrelated process.
